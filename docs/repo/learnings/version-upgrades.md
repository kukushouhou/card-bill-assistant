# 版本升级框架经验

## 完整预检先于任何迁移

- **性质**: 架构约定
- **内容**: 应用启动只根据 `installedVersion` 和 `APP_VERSION` 确定版本区间，然后对该区间全部注册迁移执行只读 `inspect`。`inspect` 是每项迁移的自定义入场条件；返回空时该迁移不进计划、不创建任务、不出现在接口或界面。禁止边检查边迁移。

## 三种迁移与全局门禁

- `silent`: 细小、确定、本地、事务性且预期必然成功；仅存在静默迁移时启动直接执行，完成后再启动同步与推送。
- `optional`: 忽略后新版本仍兼容旧数据；用户只能“现在执行/忽略迁移”。等待决策时不执行任何迁移，但正常业务、同步和推送继续。
- `required`: 仅限不迁移就影响整个系统正常运行的情况，不允许用于历史账单/卡片关系修复。以后新增必须事先显著说明必要性并取得用户明确同意，不能自行定为强制。包含这种必选迁移的计划未确认前，业务写入、邮件同步和日常提醒均等待决策。

不存在“稍后执行”。用户决定全部取得后才按版本和注册顺序执行；每个目标版本全部完成或忽略后才推进游标。游标越过后，对应迁移永久不可执行。

## 必选升级等待通知

- 调度器始终每分钟运行，在统一入口先判断升级状态：必选等待/执行期间跳过邮件同步与日常提醒，仅在尚未确认时检查升级通知；正常及迁移失败期间仍按原来的每日整点提醒、每两小时半点同步。升级开始前先切换状态、等待已有业务任务收尾，不停止或重建定时器。
- 仅对包含必选迁移、尚未确认执行的计划通知。首次从计划创建起等待 10 分钟，旧入口逐项确认/忽略则从最近一次决定起计时；页面读取和进程重启不重置。用户一旦确认开始迁移，即使部分失败也不再催办。
- 首次通知后仍未确认，从次日用户配置的每日通知时刻继续提醒；当天成功过的渠道不重复，停机错过时段或发送失败则在后续检查补发。两种通知使用同一个模板，包含目标版本以及“因为未迁移所以无法正常通知，请打开系统完成升级。”
- 使用 `NotifyLog` 的 `upgrade_pending` 类型、计划 ID、通知日期和渠道发送标识按日、按实例去重。发送失败释放自身预占，下一分钟仅重试失败渠道；异常中断的预占超过 15 分钟可接管。发送前重新核对计划，确认/执行后不再发送。沿用通知发送的租约机制，网络送达后、成功落库前崩溃仍可能重发。

## 确认执行后的失败容错

- **性质**: 最佳实践
- **背景**: 邮件修复需要区分单封原文问题、整箱不可用和执行异常；`0.5` 与 `0.8` 两项账单修复具有相同的邮箱与进度生命周期，但各自单封业务、连接重试和事务要求不同。
- **内容**: 单封邮件缺失、已删除、内容或解析失败，记录结果并跳过，保留原账单，继续其他邮件；全部跳过也能完成并推进游标，不要求恢复邮件。只有确认整箱连接/认证不可用才中断该邮箱并进入配置，其他邮箱继续；使用结构化邮箱失败标识，不能把数据库/锁错误或单封问题当授权码错误。邮箱设置沿用迁移上一级弹窗中的子弹窗和完整绑定字段，多邮箱全部验证后原子保存，再由用户点击重试，保存不自动执行、不新增常驻重试入口。故障期间保留已完成修复、释放业务门禁；重试只未完成部分，执行期等待已有业务收尾，准备/执行异常不能永久 `running`。`0.5` 历史修复保持可选，旧必选计划只更正策略元数据，不修改账单、用户决定或窗口；已完成/忽略任务不重建、不再执行。两项修复实际共用私有 `statement-repair-execution.ts`，集中承担待处理集合、按邮箱分组、账户锁、读取器生命周期、邮箱级失败分类、未完成项更新和进度汇总；关闭读取器出错也须释放锁。各迁移保留自己的单封业务和事务：旧 `0.5` 的三次连接尝试与 60 秒事务超时保持，新 `0.8` 不自动继承旧重试。数据库/事务错误在 `0.8` 单封修复中交框架失败流程，不吞成正常跳过；共享层不改写旧迁移原有单封处理语义。
- **适用范围**: 既有升级失败交互，以及 `repair-statements-050` / `repair-icbc-foreign-080` 两项账单修复的共享邮箱执行职责；不要求其他历史迁移接入，也不引入可配置迁移框架。

## 工行历史金额修正与近期还款恢复分别判定

- **性质**: 约定
- **背景**: 漏读外币应还会同时影响历史统计和待还状态；只修近期金额会遗留历史统计错误，而把全部历史账单恢复待还又会重新催收旧期次。
- **内容**: `icbc-foreign-amount-repair-080-v1` 作为 `0.8.0` 独立可选迁移，对匹配现役工行解析器且仍有邮件来源外币账单的来源邮件进行全历史复核；金额候选不限制近月、不只筛零金额，也不以外币交易存在为入场条件。只有原文确证连续币种漏读且唯一对应现存目标时，修正应还与最低还款；正确账单不重复计修正。仅还款状态恢复分支使用近期窗口及自动来源证据，窗口外只修金额并保留还款字段。迁移不整封重新入库、不补建缺失或已删账单、不重建卡片和交易关系，不改账单身份、来源、账期、出账日、还款日或币种。完成后由既有数据变更广播和服务端台账、统计、待办、提醒消费者处理，不立即发送或补发通知，不清通知去重记录。
- **适用范围**: 工行 `0.8.0` 连续币种漏读修复的已批准数据边界；全历史金额与近期恢复的范围不能自动推广成其他迁移的业务决定。

## 工行误自动结清的充分证据与最新操作保护

- **性质**: 约定
- **背景**: 错误零金额账单可能已被系统自动标为已还，但零额已还签名也不足以单独排除真实人工还款；重解析或失败重试还可能承接旧还款状态或遇到用户新操作。
- **内容**: 工行 `0.8.0` 恢复待还须同时满足：原文明确应还为正；修正前应还为零、状态为 `paid`、已还金额为零；`paidAt` 精确等于 `dueDate`；修正前最新 `updatedAt` 严格早于 `paidAt`；还款日不早于固定恢复下界。满足时改为 `unpaid` 并清空 `paidAt`、`paidAmount`。这是确认自动来源的充分条件，不是必要条件；不满足不能反向断言为人工还款，创建时间也不能替代更新时间证据。近期旧签名相似但时序不足时只修金额、保留状态并单独计 `uncertainRepayments`；正常窗口外状态保留不计入此警示。事务中重新读取当前来源、目标归属和还款字段，用修正前值判定；提交时以读取到的身份、金额、还款字段及 `updatedAt` 作条件更新，冲突保留最新操作，不覆盖失败期间的新还款、撤销、修改或删除，不从盘点快照补回目标。
- **适用范围**: 工行 `0.8.0` 已验证的旧零额自动结清路径及其修复；其他银行或旧写入机制必须重新证明，不能套用该时序签名。

## 账单修复的固定窗口与逐封原子续跑

- **性质**: 最佳实践
- **背景**: 近期恢复涉及日期窗口，迁移可能跨日失败、重启或只完成部分邮件；若窗口在重试时移动，或业务修改和任务记录分别提交，会改变恢复范围或重复修改、重复计数。
- **内容**: `0.5` / `0.8` 账单修复的还款恢复下界以首次实际执行日的上海日期固定，按上月同日、无对应日取月末计算，不等同固定 30 天；执行准备时保存 `anchor` / `lowerBound`，失败、跨日重试和重启继续使用同一下界。每封账单修改与该封任务终态、计数及原因在同一事务提交，已成功、未变化或已跳过的终态项不重跑，只处理 `pending` / `running` / `failed`。`0.8` 事务锁定任务项后复查状态，再做当前账单条件更新；其任务 JSON 保存处理身份、进度、计数和原因，不为幂等另存邮件正文、前后金额或完整还款证据副本，这一载荷边界不改写旧 `0.5` 的既有证据字段。已完成修复是实际数据副作用，降低包版本不能回滚数据，`0.8` 没有默认自动回滚副本。
- **适用范围**: 两项既有账单修复的日期、任务幂等和恢复机制；具体单封修复与状态判据仍分别由各迁移负责。

## 旧安装版本兜底

- 已安装系统缺少 `installedVersion` 且存在邮箱绑定时，按 `0.1.0` 进入历史迁移链。
- 缺少版本号且无邮箱绑定时，直接建立当前版本游标，不制造历史迁移提示。

## 升级提示文案

- 标题说清用户可见的结果；说明只保留影响范围和做决定所需的后果。户级、零账单、规则传播、迁移链和执行入口等工程术语留在开发文档中。
- 先解释旧版读错了什么、对金额/明细/待还状态有什么影响以及本次如何修复，再列实际需要复核的银行与数量；不要把“需要复核”写成已确认错误。还款恢复时间直接说明“从修复当天往前一个月起按还款日恢复待还”，不重复解释包含未来账单。
- 界面只展示“可选更新/必须更新”。静默项目完全不展示，包括混合计划中的静默标题、范围和说明；仅静默执行时也不弹进度或完成提示，但后台仍参与完整计划协调。删除等待期间同步正常等常识性说明，不在弹窗上下堆叠流程提示。
- 可选项目使用“执行/忽略”分段切换（Segmented），不使用圆形单选框；必选项目固定执行。底部一次“确认并继续”统一提交所有选择；切换选项不保存决定，不允许逐项“现在执行”，服务端整批校验和事务保存后统一启动。
- 选择顺序固定为左侧“忽略”、右侧“执行”；执行默认选中，以主题强调色表达推荐，不额外添加“推荐”字样或角标。选择忽略时使用中性色，不把忽略渲染为主题色主操作。
- 去掉常驻流程说明不等于省略操作后果。仅当用户选中“忽略”时，就近说明该项不修正会留下什么、后续新账单如何处理；结尾统一使用用户确定的“系统将不再提供本次迁移服务。”，不再拼接操作标题，也不能暗示本期问题永久延续。切回“执行”即收起警告，仍然统一确认一次。各可选迁移通过 `ignoreWarning` 提供业务后果，旧任务从当前注册项获得文案；失败后选择忽略继续使用该项具体说明，有已完成修改时另外说明会保留。
- 已保存计划和任务的展示文案按注册项读取当前定义；执行状态、用户决定、进度和业务数据不因文案修订而改变。
- 精简文案不能删掉用户的决策依据：动态展示实际受影响的银行、邮件或卡片范围与数量，并说明要做什么、读取什么、为什么读取。银行来自盘点结果及任务业务上下文，不能写死全部支持银行；邮件重读与只更新已有账单必须说清区别。通用框架通过注册项 `describeImpact` 生成 `summary`，前端必须展示；旧任务也从保存的上下文恢复该说明。
- 视觉验收须包含可选默认、历史修正和本期修正各自的忽略后果、必选单项、三种类型混合（静默不可见）、必选失败、可选失败后忽略及执行中，并分别覆盖桌面和手机。使用隔离的合成数据，必选验收示例不得注册为正式迁移；`web/e2e/upgrade-prompt.spec.ts` 保留场景与交互检查。标题与操作顶端对齐，范围和说明各占独立行，忽略后果使用无底色的就近提示，不再挤进正文侧栏。

## 账单修复结果的计数语义与计划归属

- **性质**: 最佳实践
- **背景**: 历史候选中可以同时存在已确认错误、原本正确和原文未列对应应还的账单；统一保留计数的字段名又可能被误读成原文读取失败，旧升级结果还可能冒充最近计划结果。
- **内容**: 盘点候选数不等于错误数，最终金额修正和恢复待还分别按实际任务结果累计。工行结果中的 `unavailableMails` 表示“账单未修正”的邮件数，也包括原文成功读取但未列对应外币应还的保留项；`skippedBills` 是逐目标保留数，整封保留与逐目标保留不能互换。提示说明相关记录保留原状、未修正不代表仍有错误，既不暗示所有邮件读取失败，也不据缺字段断言真实零额；金额已修正但无法确认自动来源的 `uncertainRepayments` 另行提示。`statement-repair-result.ts` 只聚合最近完成升级计划：该计划含工行修复时，仅该任务完成才返回其结果，忽略或未完成返回空，不能回退旧 `0.5`；计划不含工行修复时保持同计划原 `0.5` 结果语义，也不搜索更早计划兜底。展示旧任务的新准确说明不改写已完成任务、用户决定或业务数据。
- **适用范围**: `0.5` / `0.8` 的账单修复结果读取及展示，特别是工行金额修复的候选、保留和状态恢复计数。

## 可选工行修复等待期间的预览限制

- **性质**: 陷阱
- **背景**: 可选迁移等待时正常同步继续，用户可能跨日才执行或等待期间出现新候选；工行任务的首次盘点预览与首次实际执行准备使用不同时间点。
- **内容**: 当前 `0.8.0` 的 `inspect` 保存 `previewAnchor` 和候选数量，决定前的 `describeImpact` 基于已存载荷，不自动重盘；`prepareTask` 在首次执行时重新取得候选，并以实际开始时刻固定窗口。因此跨日等待或候选变化后，执行前展示的日期、数量可能过期。实际金额与还款判定仍按首次实际执行的窗口和最新候选，不能把预览快照当作已经冻结的执行范围。此项记录现有展示限制，不表示已实现执行前刷新，也不产生新的待实施功能。
- **适用范围**: 工行 `0.8.0` 可选修复的预览与准备时序；后续复用该时序设计时用于识别同类限制，不改变当前迁移执行契约。

## 历史邮件已删除不是迁移失败

- IMAP 返回邮件不存在或无法取得原文时，历史卡片关系迁移将对应项记为 `unchanged`，保留原账单，继续其他邮件；全部缺失仍可正常完成，不能让用户重试找不回来的邮件。
- 不存在邮件日志的明细同样跳过；存在跳过项的银行不进行旧卡孤儿清理。失败项在重试时发现邮件已删除，也应转为跳过，不保留原失败。
- 连接中断等可恢复错误仍保留失败，不能把所有读取错误一概当作邮件删除。视觉验收中的失败示例明确为连接中断，不用“邮件无法读取”笼统替代；`server/tests/card-business-relations.migration.test.ts` 通过真实读取器和迁移链验证此区别，仅替换 IMAP 传输、数据库和账单落库。
