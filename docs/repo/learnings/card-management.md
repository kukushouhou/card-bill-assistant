# 卡片管理域经验

> 套卡归组、封面选定、内部优先级、展示/匹配尾号分离、占位卡生命周期、搜索匹配、规则独立编辑、卡片版式、堆叠视觉、年费日角标、文案收敛、套卡弹窗。

---

## 套卡归组：只看规则，无账单不拆

- **性质**: 约定
- **背景**: 原 `unionFindGroups` 以 BillCard 同封为并查集归组，导致不同还款规则的卡被绑在同一套卡内。后续版本加入「辅助校验 dueDate 不一致拆出」分支，但用户决策拆套卡只看规则不看账单日期。
- **内容**: 套卡归组**只看**卡片出账日与还款规则（`statementDay + dueRule + dueDay|dueOffsetDays`）是否一致。相同即同组，不一致即拆出。**不再**用 `Bill.dueDate` 校验拆组；旧 `dueDate` 拆组代码段物理删除。账单若显示规则已变动，**先更新该卡规则**（写入 `statementDay` / `dueRule` / `dueDay` / `dueOffsetDays`），更新后规则与组内其他卡不一致再因规则不一致而拆开。**禁止**用账单还款日直接拆组。没有账单不是拆开理由——仅有卡无账单时规则相同仍组成套卡。`unionFindGroups` 仅作历史同封参考，不作为主归组依据。

## 优先显示语义重定义

- **性质**: 约定
- **背景**: 原 `isPrimary` / `primaryManual` 表示银行主副卡，承担主卡权限（规则同步、副卡只读）。用户决策剥离主副卡概念后，字段需保留但语义变更。
- **内容**: `isPrimary` / `primaryManual` 唯一业务含义为控制卡片列表中哪张卡优先显示。不再表示银行主副卡，不再承担主卡权限。`recomputePrimary` 语义变更为「归组后标记每组优先显示卡」。封面选定推导规则见「封面选定规则（pinned > priority desc > id asc）」条目（旧 billCounts 三段规则已废止）。`isBillOwner` 字段保留作标识，**不参与**自动选定。**不得**每期账单都换成当期承接卡。用户入口文案为「设为主卡」。不再向用户暴露 `isPrimary` 为标签。

## 规则每卡独立编辑

- **性质**: 约定
- **背景**: 原逻辑中主卡改规则时 `updateMany` 同步组内其他卡，副卡改规则字段返回 400。用户决策每卡独立。
- **内容**: 套卡内每张卡独立修改 `statementDay` / `dueRule` / `dueDay` / `dueOffsetDays`，不再整组同步，不再因非优先显示而只读。`PUT /api/cards/:id` 移除主卡规则同步分支。保存后归组检查新规则与组内其他卡是否一致，不一致则该卡自动拆出为独立组。错误文案「出账日/还款日规则由主卡统一管理」必须删除。

## 卡片版式规范

- **性质**: 约定
- **背景**: 原卡片正面信息顺序为「卡号 → holderName → 有效期/CVV」，卡号掩码仅 1 组 `•••• {last4}`，底部标签叫「还款日」。
- **内容**: 渲染顺序改为「卡号 → 有效期/CVV → 持卡人姓名」（holderName 下移到有效期/CVV 下方）。卡号掩码态至少 3 组 `****`（格式 `**** **** **** {last4}`）。卡片正面具体日期标签为「下一还款」；账单列表列名、待办「N 天后还款」、编辑中每月还款日字段保持「还款日」。首页与提醒中「合并 N 卡」改为「N 张卡」。

## 套卡堆叠验收（扑克牌叠放观感）

- **性质**: 约定
- **背景**: 原 `.bank-card-stack::before/::after` 用 `position:absolute + filter:brightness(0.72)` 形成背后暗化卡形伪元素，用户认为内阴影不算堆叠。后续尝试纯黑实色偏移块冒充下层卡，用户再次否决。用户验收标准是看起来像多张实体卡叠在一起。叠层下移与卡面下方原按钮行仅差约一像素，改下拉菜单后按钮行已移除，但间距数字仍需加大。上一轮把最下层卡从 11px 改到 20px（`translate Y 20px`），卡片整体突然高出一截，用户否决。
- **内容**: 套卡堆叠验收：看起来像多张实体卡叠在一起，下层卡须能看出卡面颜色（与正面同一套渐变）与圆角轮廓。**不得**内阴影、**不得**白细亮边、**不得**纯黑色块冒充下层卡。纯黑实色偏移阴影不算扑克牌叠放。保留 `.bank-card-p0..p4` 渐变与 `--card-bg` 变量。DOM 结构与点击展开行为不变。具体 CSS 实现手法（伪元素 / `box-shadow` 多层带颜色软阴影 / 额外 DOM 元素副本 / 其他）由实施决定，验收口径为最终约束。叠层与主卡之间空隙约 **1px**（只改这一处间距数字）；**不得**把最下层卡整体下移导致卡片突然高出一截、占用高度变大；**不得**再用 `translate Y 20px` 这类大幅下移；**主卡尺寸与网格位置保持与其他卡一致**；**不得**重写叠层结构、不动 `--card-bg` 变量、不动渐变、不动圆角、不动伪元素 / 阴影结构。

## 套卡年费日角标

- **性质**: 约定
- **背景**: 套卡内多张卡年费日不同，需告知用户下一笔年费何时收取以便消费达标。
- **内容**: 正面显示组内已完善年费日的卡中，下一笔将要收取的年费日。算法：按当前日期判断该月日是否已过，已过则取下一年同一月日，取 `min(diff)` 者为主显示值。全部未完善时不展示年费日角标。悬停 Tooltip 列出每张已完善卡的 `{bankName}（{cardLast4}）{M月D日}`，按日期排序，过滤 `annualFeeDate == null` 的卡。

## 文案收敛：禁止暴露底层逻辑

- **性质**: 约定
- **背景**: 多处 UI 文案暴露了合并账单、主卡统一管理、副卡只读等底层规则说明，用户认为不应暴露。
- **内容**: 禁止向用户暴露底层逻辑提示。具体删除点：`Cards.tsx` 套卡角标 Tooltip 改为「同一账期 N 张卡：xxx、xxx」；移除「主卡」/「主卡·手动」Tag；删除 `CardForm` 内「该卡属多卡账户...出账日/还款日由主卡统一管理」提示段；删除 `groupModal` 内「曾出现在同一封合并账单...」说明段；`Dashboard.tsx` / `Bills.tsx` 「合并 N 卡」Tag 改为「N 张卡」。

## 套卡弹窗响应式布局

- **性质**: 约定
- **背景**: 原套卡弹窗约 760 宽、固定两列。用户先要求 1200 宽四列，后撤回改为 960 宽三列（外层卡片管理已是四列，弹窗内再四列观感重复难看）。960 宽下大屏三列时四操作按钮溢出裁切，用户再次要求加宽。卡片操作已改为银行名称前设置图标下拉菜单，卡面下方不再平铺按钮。
- **内容**: 套卡展开弹窗约 1200 宽（`min(1200px, 94vw)`）。列数不变：窄屏一列、中屏一列、大屏两列、超宽屏三列。**不得**改回四列。弹窗内层 `<Col>` span：`xs={24} sm={24} md={24} lg={12} xl={8}`（列数 1/1/1/2/3）。外层卡片管理 `<Col>` span：`xs={24} sm={12} md={12} lg={8} xl={6}`（列数 1/2/2/3/4；中屏 sm+md 均为 2 列）。不引入 xxl 断点。标题「{bankName} · 同一账期 {N} 张卡」。弹窗内每张卡规则字段可独立编辑。`BankCardItem` 以 `plain` 模式渲染。卡片操作入口为银行名称前设置图标下拉菜单（见「卡片操作入口：设置图标下拉菜单」条目），卡面下方不再平铺按钮。

## 封面选定规则（pinned > priority desc > id asc）

- **性质**: 约定
- **背景**: 旧 `recomputePrimary` 按 `Bill.cardId` 全期累计承接次数选主卡，搜索顶替又退化为 `primaryManual + id`，两套规则不一致。用户决策引入内部优先级字段 `priority`（消费金额累加值），日常封面与搜索顶替共用同一套规则。旧 billCounts 三段规则完全废止。
- **内容**: 封面选定规则统一为：① `primaryManual=true` 且 `status='active'` 的卡永远封面（手动钉住）；② 否则按 `priority` 降序取最高者；③ `priority` 并列 → `Card.id` 升序最小者。`hidden=true` 的卡不参与候选。日常封面（`groups.main`）与搜索顶替（`pickDisplayCard` / `pickCoverCard`）共用同一套规则函数，无特例分支。`POST /api/cards/:id/primary` 只打 `primaryManual=true`，不写 `priority`，不写 `999`，不动其他卡 `priority`。手动钉住是独立状态，合账照样更新该卡 `priority`。`isBillOwner` 不参与选定。`recomputePrimary` 入参由 `billCounts` 改为 `priorities: Map<number, number>`。

## PIN 内存范围收束

- **性质**: 约定
- **背景**: 原实现将 PIN 作为全局 5 分钟 TTL 缓存在 Cards 页面 state 中，用户从未授权全局复用。关闭完善卡号弹窗时错误地把 PIN 清成空再发请求，弹出「已存信息读取失败」。
- **内容**: PIN 仅在「验证 → 完善卡号」流程中维持，流程结束即清除，**不得**全局 TTL。点眼睛 / 开其他卡需重新输入 PIN。关闭完善卡号弹窗只关窗清 PIN，**不得**再发空 PIN 读取请求。关闭路径需增加 `cancelled` 守卫（`AbortController` 或本地 cancelled state），先取消在飞请求再 `setPin('')` 再 unmount。

## 认证错误流状态码

- **性质**: 约定
- **背景**: 原实现将 PIN 校验失败、原密码错误、会话过期统一返回 HTTP 401，前端把所有 401 当登录过期跳转，导致 PIN 输错也跳登录页。
- **内容**: 401 **仅**表示未登录或登录过期（`requireAuth` 中间件）。PIN 校验失败 / 原密码错误 / 格式错 / PIN 未设 → 400。PIN 锁定 → 429。前端 `client.ts` 401 拦截器：清登录态 + `window.location.assign('/login')`（路径式，不写 hash；`client.ts` 不在 Router 树内，必须用 `window.location.assign` 而非 `useNavigate`）；`path` 含 `/auth/login` 时豁免。非 401 错误照常 `message.error` 展示。

## 新建卡留空必填

- **性质**: 约定
- **背景**: 原 `CardForm` `useEffect` 默认值段预填 `statementDay: 5, dueOffsetDays: 18`，用户决策新建卡时这些字段必须留空由用户填写。
- **内容**: 新增卡片时出账日与还款偏移必须留空必填，**不得**预填 5 号和 18 天。`CardForm` 默认值段删除 `statementDay: 5, dueOffsetDays: 18`；改用 `useState` 受控空值 + 提交前 `required` 校验。

## 卡片操作入口：设置图标下拉菜单

- **性质**: 约定
- **背景**: 原卡片操作在卡面下方平铺四个按钮（编辑、卡信息/录入卡信息、设为优先、删除），三列弹窗下按钮溢出裁切。用户决策改为银行名称前设置图标 + 下拉菜单，覆盖此前「四个按钮完整横排」验收口径。后续用户要求标题行四元素垂直居中（含年费日标签），以及设为优先必须带图标。
- **内容**: 卡片操作**不得**在卡面下方平铺按钮。**银行名称前面**加设置图标，单击展开下拉菜单。图标 `fontSize >= 1.2 × bankNameFontSize`（至少大约大 20%）。设置图标、银行名称、「N 卡」角标、年费日标签必须**同一行垂直居中对齐**（`align-items: center`），**不得**底部对齐（`align-items: flex-start`）；有年费日时该标签**必须在这一行里**，不得排除在居中行之外。点设置图标**只打开下拉菜单**，**不得**同时打开套卡弹窗（`e.stopPropagation()` 阻止冒泡到主卡点击）。下拉**五项**从上到下：**编辑 → 卡信息或录入卡信息 → 设为主卡 → 标记异常 → 删除**，五项**全部带图标**且**同一套图标风格**（具体 AntD 图标选型由实施决定）。列表封面卡与弹窗内每张卡使用**同一套**设置下拉。「设为主卡」**仅在弹窗内且该卡不是优先显示卡、且状态为正常使用时出现**（`inGroupModal === true && isPrimary === false && status === 'active'`）。「卡信息 / 录入卡信息」按 `hasSecret` 字段切换文案。「标记异常」点击后打开 `MarkAbnormalModal`（见「标记异常弹窗：按钮卡片形态 + 跨页面复用」条目）。

## 眼睛图标位置与对齐

- **性质**: 约定
- **背景**: 设置菜单引入后，需明确眼睛图标是否收进菜单。用户决策眼睛留在卡号右边专门用于查看明文，不进设置菜单。
- **内容**: 眼睛仍留在卡号右边，**不收进设置菜单**。看明文仍点眼睛，每次重新输入 PIN，卡片原地展开。眼睛与卡号**同大小**（同 `fontSize`）、**垂直居中**，并与卡号留出**合理间距**。设置菜单只管编辑、卡信息/录入卡信息、设为主卡、标记异常、删除。

## 标记异常弹窗：按钮卡片形态 + 跨页面复用

- **性质**: 约定
- **背景**: 账单行与卡片管理页均需标记卡片冻结/注销入口。用户决策弹窗形态复用 MarkPaidModal 的 OptionCard 按钮卡片风格，不得下拉/单选。编辑表单去掉状态选择，改冻结/注销只能走标记异常。
- **内容**: `MarkAbnormalModal` 弹窗 = AntD Modal + 两张按钮卡片（冻结/注销），样式复用 `MarkPaidModal` 的 `OptionCard` 视觉（边框 1.5px、圆角 8、padding 16/12、选中态 #1677ff/#f0f7ff）。**不得**用下拉框、**不得**用单选项。底部说明文字：冻结后仍可能推送未取得账单提醒；注销后该卡不再生成未取得账单。触发入口两处复用同一组件：账单行操作列「标记异常」按钮 + 卡片管理设置下拉「标记异常」项。后端复用 `PUT /api/cards/:id` body `{ status: 'frozen' | 'closed' }`，后端自动 `recomputePrimary` 让位主卡。`CardForm` 编辑表单**移除** `Form.Item name="status"` 状态选择器，改冻结/注销**只能**通过「标记异常」入口。成功提示：「已将该卡（{bankName} {cardLast4}）冻结/注销」。

## 编辑卡信息弹窗必须回填已存原信息

- **性质**: 约定
- **背景**: 卡信息弹窗编辑时，用户只改有效期或 CVV 不应被要求重新输入完整卡号。原实现未回填已存加密字段，用户必须重打完整卡号才能保存。
- **内容**: 卡信息弹窗打开时，从已存加密字段解密后回填三字段（完整卡号 / 有效期 / CVV）到对应输入框。保存时用户修改哪些字段就提交哪些字段的修改值；**未修改字段保留回填原值**。完整卡号字段即便未修改也带原值一起提交，走后端完整卡号保存闸门。只改有效期 / CVV 场景：完整卡号带原值走闸门 → 校验通过（卡号未变）→ 正常保存。用户不被强制重新输入完整卡号。

## 错误提示规范：只陈述原因，不引导操作

- **性质**: 约定
- **背景**: 蓝方审查发现前端 Luhn 校验失败报错含「请核对后重新输入」操作引导语，违反「错误提示只陈述被拒原因」决策。后端拒存文案已合规，前端是唯一偏离点。
- **内容**: 错误提示**只陈述被拒原因**，语气明确，**不得**引导或建议用户执行任何操作，尤其**不得**出现「删除后重建」引导（删除重建与否是用户自由，系统不得推荐）。粗略口径落地时按语义润色为表述自然、有明确主语的正式提示，不逐字照搬。后端拒存文案：「该卡已记录的账单尾号为…，与本次录入的完整卡号不符」（统一语义，不区分场景细说）。前端 Luhn 校验失败：「该卡号未通过卡号校验」（仅陈述事实，无操作引导）。

## 搜索匹配字段集：只按展示尾号，不按匹配尾号

- **性质**: 约定
- **背景**: 展示尾号（`displayLast4`）与匹配尾号（`cardLast4`）分离后，搜索字段集需明确只用展示尾号。匹配尾号仅用于邮件账单匹配，不参与搜索。
- **内容**: 卡片列表本地搜索按四字段不区分大小写子串匹配：`displayLast4`（展示尾号）、`bankName`、`nickname`、`holderName`。**不**按 `cardLast4`（匹配尾号）搜索。纯文本搜索，不得为 1-3 位纯数字另设末尾子串或精确四位匹配规则。`----` 按文本参与搜索。搜索与排序直接作用当前卡片网格，不另建搜索结果页。

## 内部优先级（priority）计算

- **性质**: 约定
- **背景**: 旧主卡规则按承接账单次数选封面，无法反映消费权重。用户决策引入 `priority` 字段记录消费金额累加值，用于封面选定与搜索顶替。红方审查发现原实现直接累加 `t.amount` 未排除负值，与「只记消费金额」决策意图偏离。
- **内容**: `Card.priority`（`Float @default(0)`）= 该卡消费金额累计值。新卡从 `0` 起。与账单金额同一量纲。不向用户展示，不做表单。合账时**累加式**写入（现有值 + 本期金额），不按全部已入库账单重算总额。有明细时每张卡**只加正数消费和费用**——每笔先做 `amount > 0` 过滤，按卡尾分组求和；**0 / 负数 / 冲抵 / 返还 / 还款一律不扣分**（0 不是正数，跳过）。无明细时按该期总金额计入该卡。同一期幂等（依赖 `Bill.cardId + period` 唯一约束，重复入库不累加）。手动钉住（`primaryManual=true`）的卡照样更新 `priority`。不再使用承接卡（owner）给整期总额加分。多卡无明细不单独立法（现役解析器多卡都带金额）。不回填现有库；任务收口后清库全量重拉。

## 展示尾号与匹配尾号分离

- **性质**: 约定
- **背景**: 原 `cardLast4` 同时承担邮件匹配和用户展示职责。占位卡完善后需区分「给用户看的尾号」和「用于邮件匹配的尾号」。红方审查发现 secret 路由在占位 + 展示尾号已有四位时静默丢弃更新、已完善卡后四位不一致时静默写入；蓝方审查发现编辑接口 zod schema 仍定义 `cardLast4` 字段但处理器丢弃，形成校验缝隙。
- **内容**: `cardLast4`（匹配尾号）用于邮件账单匹配；占位为 `----`；**编辑时只读**。`displayLast4`（展示尾号）给用户看、用于搜索；占位时默认 `----`。匹配尾号不是占位时，展示尾号**必须**与匹配尾号一致。匹配尾号仍是占位时，展示尾号保持默认 `----`，**只能**靠录入完整卡号自动生成（取后四位）。完善占位卡**只能**通过卡信息弹窗录入完整卡号，由系统自动生成 `displayLast4`；`cardLast4` 保持 `----` 不变；不删占位卡。**不得**通过编辑后四位字段来完善占位卡。编辑表单中后四位字段只读（`disabled={!!initial}`）；新建时才能输入；来自邮件账单生成的卡不能改后四位；要改后四位只能删除后重建。

### 完整卡号保存闸门（多层防护）

录入完整卡号（`POST /api/cards/:id/secret`）时按匹配尾号分闸：

- **前端 Luhn 校验**（必经门）：自实现纯函数 `isValidCardNumber`，校验 13–19 位数字串；非全数字直接判失败。未通过时禁用提交并明确报错（仅陈述原因，不引导操作）。
- **后端分闸兜底**（按当前 `cardLast4` 与 `displayLast4` 状态）：
  - 匹配尾号已是真号（`cardLast4 !== '----'`）：录入完整卡号后四位**必须** `===` 现有 `cardLast4`，否则拒绝保存。
  - 匹配尾号是占位符 + `displayLast4 === '----'`：由完整卡号后四位写入 `displayLast4`（仅这一次）。
  - 匹配尾号是占位符 + `displayLast4` 已有四位：拒绝保存（不允许 A→B 变更）。
- **关键不变量**：保存闸门落地后，加密卡号后四位 `===` `displayLast4` `===`（匹配尾号是占位时 `cardLast4='----'`；匹配尾号是真号时 `cardLast4` 后四位）。

### 编辑接口校验层拒收后四位

- 编辑卡片 zod schema（`cardUpdateSchema`）使用 `.omit({ cardLast4: true }).strict()`：接口校验层**不再接受** `cardLast4` 字段，传入即 400 拒绝（即使值与现有相同）。
- 前端表单 `disabled` + 提交时移除字段 + 接口拒收形成**三层防护**。
- 处理器不接收、也不丢弃 `cardLast4`；直调 API 也无法写入或修改。

## 占位卡生命周期四路径

- **性质**: 约定
- **背景**: 旧逻辑「新账单带真号就删占位卡」与「删卡级联删账单」冲突。用户决策改为四条独立路径，适用范围不同，分别生效，后写不能覆盖前写。
- **内容**:
  - **路径 1 — 未完善占位卡隐藏**：用户未完善（`displayLast4` 仍 `----`）的占位卡，与同银行任一真实卡的 `statementDay + dueRule + dueDay|dueOffsetDays` 一致 → **隐藏**该占位卡（`hidden=true` 持久化标记，不物理删除）。隐藏条件不比较账单月份；账单仍挂在这张卡上、不改挂、不跟着消失。隐藏后卡片管理里完全消失（网格 / 搜索 / 套卡弹窗 / 编辑 / 设为主卡 / 录入完整卡号全部不可见不可操作）。`hidden` 标记对用户不可见、无标签、无恢复入口（界面单向）。隐藏 ≠ 冻结 ≠ 注销（冻结/注销仍出现在卡片列表并带标签）。
  - **路径 2 — 手动完善（录入完整卡号）**：用户通过卡信息弹窗录入完整卡号 → 前端 Luhn 校验先行拦截 → 后端按匹配尾号分闸（见「展示尾号与匹配尾号分离 → 完整卡号保存闸门」条目）：真号必须后四位一致；占位 + 展示尾号空则这一次写入 `displayLast4`；占位 + 展示尾号已有四位则拒绝（不可 A→B）。`cardLast4` 保持 `----` 不变；不删占位卡。
  - **路径 3 — 已完善卡碰真号（匹配尾号必须升级）**：用户已完善（`displayLast4` 为具体四位）+ `cardLast4` 仍为 `----` + 新邮件真号与 `displayLast4` 相同 → `cardLast4` **必须**从 `----` 变更为该真实尾号（写硬，不是可选项）；`displayLast4` 同步。
  - **路径 4 — 已完善卡真号与展示尾号不同**：用户已完善 + 新邮件真号与 `displayLast4` 不同 → 直接创建新卡档案；不删已完善卡、不挂到已完善卡。
  - **历史账单**：占位卡上已入库的历史账单不迁移、不改挂、不跟着消失；按银行名仍可查找。存量违规可见占位卡通过版本静默迁移只修正隐藏状态，不清库、不重拉。

## 已完善卡碰真号：匹配尾号升级与建新卡

- **性质**: 约定
- **背景**: 用户手动完善占位卡后（`displayLast4` 为具体四位，`cardLast4` 仍 `----`），银行后续可能开始发带真实尾号的账单。需明确匹配尾号如何从占位升级。
- **内容**: 已完善卡（`displayLast4` 为具体四位 + `cardLast4` 仍 `----`）碰新邮件真号时：真号与 `displayLast4` **相同** → `cardLast4` **必须**从 `----` 变更为该真实尾号（写硬），`displayLast4` 同步；此后展示尾号与匹配尾号一致，后续同号账单自动挂到该卡。真号与 `displayLast4` **不同** → 视为另一张新卡，直接创建新卡档案；**不删**已完善卡、**不挂**到已完善卡。

## 删卡级联删账单

- **性质**: 陷阱
- **背景**: 删卡操作会连带删除该卡上所有账单，因 `Bill.cardId` 设了 `onDelete: Cascade`。用户决策占位卡历史账单必须保留。
- **内容**: 删卡会连带删除该卡上所有 `Bill` 记录（`Bill.cardId onDelete Cascade`）。要留账单就**不能**物理删卡。占位卡隐藏用 `hidden=true` 标记代替物理删除，正是为了避免级联删账单。前端删除按钮须确认提示，告知用户删除后账单也会消失。

## 决策总线适用范围：后写不盖前写

- **性质**: 约定
- **背景**: 占位卡生命周期从「自动删除」演化为「隐藏」，已完善卡双路径（同尾号升级 / 不同尾号建新卡）独立存在。多条决策适用范围不同，需明确不互相覆盖。
- **内容**: 决策总线中适用范围不同的决策**分别生效**，后写不能盖前写。具体：
  - 未完善占位卡隐藏（路径 1）与已完善卡双路径（路径 3 + 路径 4）是**两条独立规则**，各自有独立前提条件和触发条件。路径 4「不删已完善卡」不覆盖路径 1「隐藏未完善占位卡」；路径 1「隐藏」也不覆盖路径 3「匹配尾号升级」。
  - 「保存完整卡号时不写匹配尾号」（完整卡号保存闸门：匹配尾号保持 `----`，只写 `displayLast4`）与「等新邮件同尾号再变更为该尾号」（路径 3 匹配尾号升级）是**两条独立规则**，各自有独立前提条件和触发条件。保存闸门不覆盖匹配尾号升级；匹配尾号升级也不覆盖保存闸门。
  - 实施时必须逐路径独立判断，不得合并或互相替代。
