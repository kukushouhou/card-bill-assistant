# 解析入库域经验

> 平安附卡持卡人独立收录、无卡号占位符 `----`、占位档案切归属。

---

## 平安附卡持卡人按卡区块独立写入

- **性质**: 约定
- **背景**: 原 `pab-2026` 解析器 `pickHolder(text)` 只取账单抬头姓名，附卡被错误覆盖为主卡持卡人姓名。平安账单按卡区块划分，每个区块已写明该卡持卡人姓名。
- **内容**: 解析端构建按卡尾号的 `holderMap`：主卡区块从 `pickHolder(text)` 取；附卡区块从「附卡 Sup Card 附卡人：XXX」提取。`ParsedBill` 类型扩展可选的按卡尾号姓名映射字段。`pipeline.applyParsedBill` 写入规则：对每个 tail，若 `holderMap[tail]` 存在则写入对应 `Card.holderName`（已有值不覆盖）；无映射且 `!card.holderName` 时回落到 `bill.holderName`（兼容非平安银行）。不新增 schema 字段，复用现有 `Card.holderName`。平安附卡区块无「附卡人：XXX」时不写入该映射。

## 无卡号占位符改为 `----`

- **性质**: 约定
- **背景**: 原用 `0000` 作为无卡号占位，与真实卡号 0000 冲突。浦发全部、北京 2021-2022、南京 2023-2025、招商 2016-2020、平安 2021-2022 摘要式均经原文确认无卡号可提取。
- **内容**: 解析器 `buildBill` 中 `cardLast4` 无法提取时使用 `----` 替代 `0000`。`applyParsedBill` 中 `tail === '0000'` 判定改为 `tail === '----'`。`Card` 唯一约束 `[bankName, cardLast4]` 中 `----` 作为占位标识。多卡尾并存时 `0000` 是银行费用行占位（如招行会员费）需剔除；明细全是 `0000` 时保留档案占位 `----`（浦发正文无卡号）。新解析用 `----`；历史库由用户授权清库后全量重拉重建；**不在**开发中途刷 0000 字符串，也**不**强制批量迁移历史 0000。清库范围 = Card / Bill / BillCard / MailLog；保留 Admin / AppSetting / EmailAccount / CustomReminder。清库脚本命名 `tmp-*`，执行前需用户显式授权 + 物理备份。

## 占位档案切归属逻辑（已被 card-management.md「占位卡生命周期四路径」取代）

- **性质**: 约定
- **背景**: 早期无卡号 `----` 占位档案在后续账单读到真实卡号时需要自动合并。本轮改造引入展示尾号/匹配尾号分离 + 未完善占位卡隐藏机制，旧「删除占位卡」逻辑已废止。
- **内容**: 占位卡完整生命周期已迁移至 `card-management.md`「占位卡生命周期四路径」条目。核心变更：未完善占位卡（`displayLast4` 仍 `----`）同账期出现真尾号卡时改为**隐藏**（不物理删除，因删卡会级联删账单）；已完善卡碰真号时匹配尾号必须升级；真号与展示尾号不同时建新卡不删已完善卡。本条目保留为历史索引，不再作为执行依据。

## applyTransactionTails 对 `----` 无对称剔除

- **性质**: 陷阱
- **背景**: `applyTransactionTails` 对 `0000` 有剔除逻辑（多卡尾并存时 0000 是银行费用行占位需剔除），但占位符改为 `----` 后该函数无对称处理。
- **内容**: `applyTransactionTails` 当前对 `----` 无对称剔除逻辑。后续若多卡尾并存场景中出现 `----` 占位行，需确认是否需要与 `0000` 同等剔除。本次手术边界外，待后续任务处理。

## POST 建卡 schema 拒 `----`

- **性质**: 陷阱
- **背景**: `POST /api/cards` 的 schema 校验仍拒 `----` 作为 `cardLast4` 值，pipeline 直写数据库绕过了 schema 校验。
- **内容**: `POST /api/cards` schema 仍拒 `----`，pipeline 通过 Prisma 直写绕路。若后续需要通过 API 创建占位卡，需同步更新 schema 校验。本次手术边界外。

## 平安抬头无姓名且附卡无附卡人时的回落

- **性质**: 陷阱
- **背景**: 平安账单抬头无持卡人姓名，且附卡区块无「附卡人：XXX」标注时，当前逻辑不回落到抬头姓名。
- **内容**: 平安抬头无姓名且附卡无附卡人时，不回落到抬头姓名（因为抬头本身也无姓名）。解析端 `holderMap` 中该附卡尾号无映射，`applyParsedBill` 写入时 `!card.holderName && bill.holderName` 回落条件也不满足（`bill.holderName` 为空）。该卡 `holderName` 保持为空。本次手术边界外，待后续确认是否需要提示用户手动补全。

## 解析器全部字段零兜底

- **性质**: 约定
- **背景**: 原部分解析器在取不到字段时会调用兜底函数（如 `pickHolder` 兜底姓名、按消费金额猜卡号归属）。用户决策解析器一律不猜，取不到留空。
- **内容**: 全部现役解析器对**全部字段**（持卡人 / 卡号 / 其他）取不到时一律 `null` / `undefined`；不调用兜底函数，不猜归属。解析器零兜底；落库兜底全部在合账阶段（`pipeline.applyParsedBill`）：合账三档顺序 = `holderMap` → 历史 → 同封主卡。空卡号按出账日匹配已有 `----` 档案、真实卡号 + 出账日一致切归属，全部在合账阶段完成。

## 称呼行真实姓名提取（非兜底）

- **性质**: 约定
- **背景**: 解析器从邮件称呼行（如「尊敬的 XXX 先生」）取出真实姓名，曾被误判为禁止的解析器兜底。用户决策明确这是提取已写明的姓名，不是兜底。
- **内容**: 邮件称呼行**写明真实姓名**时，解析器可以提取并写入该封账单持卡人，这**不是兜底**。没写姓名或「客户您好」一类通用称呼继续留空（`pickHolder` 现有过滤返回 `null`）。合账阶段**不得**用抬头姓名覆盖附卡已有姓名。`pickHolder` 函数保留作称呼行真实姓名提取用途。

## 招行费用行特例

- **性质**: 约定
- **背景**: 招行账单中银行费用行（如会员费）卡尾写成 0000 且无交易地标识，而消费行有交易地 CN。需要精确区分费用行与有真实卡号 0000 的消费行。
- **内容**: 只有招商银行作为特例：明细末四位为四个零**且**交易地为空，才视为没卡号（`cardLast4 = null`）。判定条件 = `cardLast4 === '0000' && 紧接 0000 后的 CN 字段为空`；两者必须同时满足。识别原文形态：会员费行 0000 后无 `CN`，消费行 3096 后有 `CN`。覆盖**全部**招行解析器（`cmb-2026` / `cmb-2020` / `cmb-2016` 等现役版本）。民生 / 海南 / 其他银行**不**按招行特例改。`applyTransactionTails` 既有「多卡尾剔除银行费用行 0000」机制保留不修改。

## 中信运通卡卡尾取明细末四位

- **性质**: 约定
- **背景**: 中信银行运通卡账单抬头印 `3780-09**-****-855`（3 位），但交易明细「卡号后四位」列为完整末四位 `8855`。此前「邮件原文就是 3 位、按原文保持」决策作废。
- **内容**: 中信全部解析器（`citic-2023` / `citic-2020` / `citic-2026` 等现役版本）卡尾必须取交易明细「卡号后四位」四位数字（如 `8855`），**不得**用抬头掩码最后一组 3 位（如 `855`）。`buildBill` 接收解析器传入的四位卡尾，不回退抬头。测试期望从 `855` 改为 `8855`，并锁住「来源=明细末四位」。

## 费用行/分期解析阶段卡号留空，合账挂优先显示卡

- **性质**: 约定
- **背景**: 原部分解析器在费用行填 0000、分期行猜卡号归属。用户决策解析阶段一律留空，合账确定套卡配置后再挂优先显示卡。
- **内容**: 费用行 / 分期 / 其他账户级区块在解析阶段卡号留空（`cardLast4 = null`），**不得**填 `0000` 或 `----`。合账阶段（`pipeline.applyParsedBill`）在已能确定套卡配置后（归组完成 + 自动选定 `isPrimary`），将无卡号交易统一挂到该套卡优先显示卡（封面选定规则：`primaryManual` ? 该卡 : `priority` 降序最高者 : 并列时 `id` 升序最小者；详见 `card-management.md`「封面选定规则」条目）。禁止解析器按消费加总做归属兜底。
