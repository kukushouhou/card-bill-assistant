# v0.2.2

- 发布日期：2026-08-31
- 对比版本：v0.2.1
- 完整差异：[v0.2.1...v0.2.2](https://github.com/kukushouhou/card-bill-assistant/compare/v0.2.1...v0.2.2)

## 版本概述

`v0.2.2` 是一次 Docker 部署紧急修复版本。`v0.2.1` 镜像已经打包 Web 前端，但镜像内的前端实际目录与服务端默认查找目录不一致，导致容器和 API 均能正常启动、健康检查也显示正常，访问根地址却返回 `路径不存在: GET /`。本版本修正前端静态资源路径，并将首页纳入容器健康检查，确保“容器健康”同时代表 API 与 Web 入口均可访问。

本版本不改变信用卡账单、交易明细、提醒、通知渠道或认证逻辑，也没有数据库结构和数据迁移。

## 详细变更

### 1. 修复 Docker Web 首页无法访问

- 生产镜像现在显式设置 `WEB_DIST_DIR=/app/web/dist`，与 Dockerfile 实际复制的前端构建产物目录保持一致。
- 内置 MySQL 与外置 MySQL 两份 Compose 均显式传入同一前端目录；这也可以修复已经包含前端产物但未找到目录的 `v0.2.1` 镜像。
- 使用官方镜像、内置 MySQL、外置 MySQL 或通过 `docker-compose.build.yml` 从源码构建时，均使用相同的前端目录契约。
- 默认 Docker 镜像不依赖 Nginx 伪静态；Node 服务会把 `/login`、`/cards`、`/bills` 等非 `/api` 深层链接回退到 `index.html`，浏览器直接打开或刷新这些页面不会返回服务端 404。

### 2. 消除容器假健康状态

- 应用健康检查不再只请求 `/api/health`，同时请求 Web 根地址 `/` 和前端路由 `/login`，并确认两个页面均返回 HTML。
- API 正常但前端未被托管，或前端深层链接无法回退到 `index.html` 时，应用容器会被标记为不健康，不再出现页面不可访问而容器仍显示健康的误导状态。

### 3. 增加镜像构建回归保护

- CI 在生产镜像构建后读取镜像内的 `WEB_DIST_DIR`，并检查该目录下存在 `index.html`。
- 前端目录环境变量、Dockerfile 复制目标或构建产物任一再次不一致时，Docker CI 会直接失败，阻止错误镜像进入发布流程。

### 4. 同步部署与升级文档

- README、部署指南、AI 部署提示词、Compose 默认版本、环境变量示例以及前后端项目版本统一更新为 `0.2.2`。
- 升级备份流程进一步明确为由数据库变更触发：全新安装或无数据库变更的升级不询问备份；只有目标版本包含结构或数据迁移时才询问并推荐备份，内置与外置 MySQL 使用同一判断标准。

## 升级说明

- 从 `v0.2.1` 升级时，保留原有 `.env`、`ENCRYPTION_KEY`、数据库和 Docker 数据卷，将 `APP_VERSION` 改为 `0.2.2` 后重新拉取并启动容器。
- 内置 MySQL：执行 `docker compose pull`，然后执行 `docker compose up -d`。
- 外置 MySQL：执行 `docker compose -f docker-compose.external.yml pull`，然后执行 `docker compose -f docker-compose.external.yml up -d`。
- 源码构建部署需要拉取 `v0.2.2` 代码并使用原有双 Compose 文件命令增加 `--build` 重新构建。
- 本版本没有新增 Prisma 迁移，不需要数据库备份、数据清理、回填或全量重拉。
- 升级后可通过浏览器访问根地址并直接打开或刷新 `/login`，再使用 `docker compose ps` 确认应用容器健康；不要只检查 `/api/health`。

## Docker 镜像

- 固定版本：`ghcr.io/kukushouhou/card-bill-assistant:0.2.2`
- 同步标签：`ghcr.io/kukushouhou/card-bill-assistant:0.2`、`ghcr.io/kukushouhou/card-bill-assistant:latest`
- 支持平台：`linux/amd64`、`linux/arm64`
- 内置 MySQL：使用 `docker-compose.yml`
- 外置 MySQL：使用 `docker-compose.external.yml`

生产环境建议固定使用 `0.2.2`，不要长期跟随 `latest`。升级时不得更换已经用于加密数据的 `ENCRYPTION_KEY`。

## 已知限制

- 银行邮件解析能力以 README 中已经校准的模板为准；银行调整邮件格式后可能需要新增版本化解析器。
- 浦发银行邮件不包含可直接解析的交易明细，跳转页需要短信验证，因此只能获取账单摘要，无法自动抓取交易明细。
- 未出账单日度明细目前仅支持招商银行“每日信用管家”，且只同步本账期数据。
- 纯 HTTP 访问不提供传输加密；建议通过 HTTPS 反向代理使用。

除上述既有边界外，本版本没有新增已知限制。
