# v0.2.1

- 发布日期：2026-08-31
- 对比版本：v0.2.0
- 完整差异：[v0.2.0...v0.2.1](https://github.com/kukushouhou/card-bill-assistant/compare/v0.2.0...v0.2.1)

## 版本概述

`v0.2.1` 是一次通知配置边界与公开部署体验的整理版本。相较 `v0.2.0`，本版本彻底删除了尚未形成正式使用历史的 Bark 环境变量、旧设置接口和单渠道安装参数，不再保留没有实际用户迁移需求的兼容分支；所有通知渠道统一通过 Web 安装向导或系统设置管理，并使用 `ENCRYPTION_KEY` 加密保存。同时重新整理 AI 协助部署、图形化 Docker 管理界面和手动部署文档，使首次安装、外置 MySQL 与通知渠道配置各自回到正确的流程边界。

本版本没有改变现有的信用卡账单解析、卡片管理、提醒周期和多渠道推送能力，也没有数据库结构迁移。

## 详细变更

### 1. 统一通知渠道配置

- 通知渠道继续支持 Bark、ntfy、Gotify、Telegram Bot、Server酱、PushPlus、企业微信机器人、钉钉机器人、飞书机器人和自定义 HTTP 推送。
- 所有渠道现在只从数据库中的 `NotificationChannel` 读取；新增、启用、停用、测试和删除均通过当前通用通知渠道接口完成。
- 渠道配置必须是由 `ENCRYPTION_KEY` 加密后的密文信封。读取到不符合当前加密格式的数据时会明确报错，不再把任意明文 JSON 当作有效配置继续使用。
- 系统设置页移除了渠道来源兼容标识，直接显示“已启用”“已停用”或“未配置”，避免把内部存储来源暴露给用户。
- 安装向导只提交当前的 `notifications` 数组；可一次配置多个不同渠道，也可以提交空数组直接跳过，后续仍可在系统设置中添加。

### 2. 删除无实际迁移需求的临时兼容分支

- 从 Docker Compose、环境变量示例、环境生成脚本和服务端配置中删除 `BARK_URL`。
- 删除只为单一 Bark 地址服务的旧通知模块，以及对 `AppSetting.barkUrl` 的读取和迁移逻辑。
- 删除 `notificationChannelsInitialized` 状态标记及相关回退判断。
- 删除旧版 `PUT /api/settings` 中的 `barkUrl` 写入方式和 `POST /api/settings/test-bark` 测试接口。
- `GET /api/settings` 不再返回 `barkUrl`，前端类型和设置页也不再保留对应回退代码。
- 删除安装接口的单数 `notification` 参数和特殊的 `none` 渠道值，只保留当前多渠道数据结构。

### 3. 修正 AI 协助部署流程

- README 将“使用 AI 协助部署”放在部署方式首位并标记为推荐，同时提供可直接复制到任意 AI 工具的一段完整入口提示词。
- 入口提示词直接链接仓库根目录的 `AI_DEPLOYMENT_PROMPT.md`，由 AI 读取实际 Compose、环境变量示例和部署文档后再收集必要信息。
- 部署阶段不再询问 Bark 或其他通知渠道。应用启动后，用户直接在 Web 安装向导中添加一个或多个通知渠道，或自行跳过。
- 外置 MySQL 模式只确认连接信息、空数据库和建表/迁移权限，不再询问备份目录、要求备份权限或把外部数据库备份列为应用部署交付项。
- 内置 MySQL 的升级恢复点与外置 MySQL 的既有备份制度分别说明，避免把两种数据库模式混为一谈。
- AI 部署提示词继续要求在覆盖 `.env`、更换 `ENCRYPTION_KEY`、删除数据卷或执行破坏性操作前停止，并向用户说明安全与数据影响。

### 4. 完善 README 与手动部署入口

- 标题区域增加 CI、Release、License、GHCR、平台架构和 Node.js 版本徽章。
- README 开头增加目录锚点，长页面可以直接跳转到完整功能、银行支持、界面预览和各类部署方式。
- 在开头独立提供“完整功能”栏目，集中说明邮件同步与解析、卡片中心、账单和交易明细、年费显著提醒、常规提醒、固定账单、动态账单、丰富周期、今日待办、未来日程、多渠道推送和自动任务。
- 明确项目同时适配电脑、手机与平板触屏端，并补充卡片中心电脑端和首页触屏端效果图。
- 图形化 Docker 管理界面可以直接打开内置 MySQL、外置 MySQL 和环境变量源文件页面，复制仓库中的完整最新内容后粘贴到 Stack、项目或编排任务。
- 手动部署说明覆盖官方 Docker 镜像、Docker 源码构建和不使用 Docker 的 Node.js 源码部署，并分别给出内置/外置 MySQL 入口。
- 浦发银行支持说明已修正：邮件仅提供摘要；交易明细跳转页需要短信验证，因此本服务无法自动抓取，而不是暂缓抓取。

### 5. 固化后续发布质量要求

- 新增仓库级中文发布规范，要求每个版本以最近正式标签为基线，完整记录变化、升级影响、镜像信息、验证结果和已知限制。
- 容器发布工作流会强制检查 `docs/releases/vX.Y.Z.md` 是否存在并包含必要中文章节；不符合要求时不会继续发布。
- 多架构镜像成功推送后，工作流使用该版本说明创建或更新 GitHub Release，避免发布页只剩自动生成的提交标题。

## 升级说明

- 从 `v0.2.0` 升级时，将 `APP_VERSION` 改为 `0.2.1` 后重新拉取并启动容器；必须保留原来的 `.env`、`ENCRYPTION_KEY` 和数据库数据。
- 本版本没有新增 Prisma 数据库迁移，不需要手工执行数据修正或回填。
- `BARK_URL` 已不再读取。如果曾经只在环境变量中填写 Bark 地址，需要在 Web 安装向导或“系统设置 → 通知渠道”中重新添加 Bark。
- 直接调用旧设置接口的自建脚本需要改用 `/api/settings/notification-channels/:type` 和 `/api/settings/notification-channels/:type/test`。
- 如果数据库中存在未加密的通知渠道配置，本版本不会自动迁移；应在升级前通过当前设置页面重新保存渠道配置，或删除后重新添加。正常通过 `v0.2.0` 当前多渠道界面保存的配置已经是加密格式，不受影响。
- 使用外置 MySQL 时，应用账号仍需连接目标数据库并执行现有迁移所需的建表/变更权限，但不需要具备数据库备份权限。

## Docker 镜像

- 固定版本：`ghcr.io/kukushouhou/card-bill-assistant:0.2.1`
- 同步标签：`ghcr.io/kukushouhou/card-bill-assistant:0.2`、`ghcr.io/kukushouhou/card-bill-assistant:latest`

- 外置 MySQL：使用 `docker-compose.external.yml`

生产环境建议固定使用 `0.2.1`，不要长期跟随 `latest`。升级时不要更换已经用于加密数据的 `ENCRYPTION_KEY`。

## 已知限制

- 银行邮件解析能力以 README 中已经校准的模板为准；银行调整邮件格式后可能需要新增版本化解析器。
- 浦发银行邮件不包含可直接解析的交易明细，跳转页需要短信验证，因此只能获取账单摘要，无法自动抓取交易明细。
- 未出账单日度明细目前仅支持招商银行“每日信用管家”，且只同步本账期数据。
- 纯 HTTP 访问不提供传输加密；建议通过 HTTPS 反向代理使用。外置 MySQL 的备份与恢复由数据库管理方负责，不属于本应用的部署能力。

除上述边界外，本版本没有新增已知限制。
