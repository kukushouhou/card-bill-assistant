# v0.3.2

- 发布日期：2026-09-01
- 对比版本：v0.3.1
- 完整差异：[v0.3.1...v0.3.2](https://github.com/kukushouhou/card-bill-assistant/compare/v0.3.1...v0.3.2)

## 版本概述

`v0.3.2` 修复了占位卡已有同周期真实卡时仍出现在卡片中心的问题。系统现在按同银行、同出账日和同还款规则判定占位卡是否应隐藏，不再使用正常业务中无法成立的“相同账单月份”条件。占位卡只改变可见状态，原有账单、金额、日期、来源邮件和还款状态全部保留。

本版本同时建立了长期版本升级框架。后续版本可为每项迁移声明自定义只读入场条件，并根据影响划分为静默、可选和必选迁移；不满足入场条件的迁移不会进入计划、不会创建任务，也不会向用户弹出提示。

## 详细变更

### 1. 修复占位卡隐藏生命周期

- 未完善占位卡与同银行真实卡的出账日和还款规则一致时，持久化为隐藏状态。
- 删除“占位卡与真实卡必须拥有同月份账单”的不可达条件。
- 隐藏时只清除占位卡的优先展示标记；不删卡、不迁移账单、不改写交易明细。
- 没有兼容真实卡的银行继续保留 `----` 作为合法卡片身份；用户已完善展示尾号的档案不参与自动隐藏。
- 邮件合账、新增真实卡以及修改出账/还款规则都复用同一套占位卡协调规则。

### 2. 建立长期版本升级框架

- 启动时依据 `installedVersion` 与当前版本确定完整迁移区间，先完成所有只读入场检查，再决定全局升级状态。
- 静默迁移只允许承载细小、本地、确定且可在单个事务内完成的修正。
- 可选迁移只允许用户“现在执行”或“忽略迁移”；版本游标越过后永久不能再执行。
- 必选迁移需要用户主动确认且不能忽略；确认前所有迁移、邮件同步和提醒推送均暂停。
- 仅存在可选迁移且等待用户决定时，日常同步、业务更新和提醒推送继续运行；真正迁移执行期间统一暂停新写入。
- 缺少版本号但存在邮箱绑定的旧安装按 `0.1.0` 进入历史迁移链；没有邮箱绑定时直接建立当前版本游标。

### 3. 通用升级任务与门禁

- 新增通用升级计划、任务及明细数据结构，保存迁移类型、版本、用户决定、进度、错误和通用业务上下文。
- 原有主卡/副卡历史重解析纳入可选迁移，仅在数据库存在对应解析器的已匹配历史账单时才出现。
- 升级页面使用通用任务信息，明确标识静默、可选和必选迁移，并展示决策与执行进度。
- 健康检查区分进程存活与业务就绪，避免必选迁移门禁导致容器被误判为崩溃。

### 4. 增强测试与规则文档

- 服务端增加版本比较、完整预检分类、入场条件、旧安装版本兜底和占位卡协调回归测试。
- 占位卡回归用例改为“旧月份产生占位卡，后续月份出现真实卡”的真实生命周期，删除伪造同月份状态的测试前提。
- 项目开发规则和领域经验文档同步收敛到“隐藏、不删除、不改挂”的现行规则。

## 升级说明

- 从 `v0.3.1` 升级时，必须保留原有 `.env`、`ENCRYPTION_KEY`、数据库和 Docker 数据卷。
- 本版本包含 Prisma 数据库结构迁移，用于将原有主副卡专用升级任务改造为通用版本升级计划和任务结构。容器启动时会自动执行 `prisma migrate deploy`。
- 结构迁移完成后，`0.3.2` 静默迁移会只隐藏已有兼容真实卡的未完善占位卡，并重算组内优先展示卡。不会删除卡片、迁移账单或重新解析历史邮件。
- 已有主副卡历史迁移任务会保留原有状态和进度；版本游标已经越过其目标版本的未完成旧任务不会再执行。
- 本版本不需要清库、全量重拉或手动执行数据修复脚本。
- 升级前建议完成数据库备份。版本游标升至 `0.3.2` 后，旧版本程序会拒绝对较新数据库执行反向迁移；如需回滚到 `v0.3.1`，应同时恢复升级前的数据库备份。
- 内置 MySQL：执行 `docker compose pull`，然后执行 `docker compose up -d`。外置 MySQL：使用 `docker-compose.external.yml` 执行相同的拉取与启动流程。

## 已知限制

- 占位卡隐藏仅在同银行的出账日与还款规则完全一致时发生；没有兼容真实卡的无卡号账户仍使用 `----` 作为身份。
- 主卡、副卡和附属卡历史重解析仍需要原邮件可从已绑定邮箱读取；邮件已删除时对应项会保留原数据并记为无变更。
- 本版本没有新增邮件模板支持范围或外部通知渠道。`v0.3.1` 已说明的邮件模板识别、上游依赖、浦发账单明细、招商银行未出账明细和 HTTP 传输边界仍然适用。
