# v0.3.0

- 发布日期：2026-08-31
- 对比版本：v0.2.3
- 完整差异：[v0.2.3...v0.3.0](https://github.com/kukushouhou/card-bill-assistant/compare/v0.2.3...v0.3.0)

## 版本概述

`v0.3.0` 新增银行业务主卡、副卡和附属卡的独立建模。系统现在能够在银行账单明确提供关系时，把整组卡片归入固定的业务主卡：主卡统一承接账单、还款状态和提醒，副卡与附属卡保留各自的卡片资料、持卡人规则和年费日，不再产生重复账单或重复提醒。

首批支持工商银行、平安银行和广发银行的现役明确关系模板。工商银行的手机信用卡不会创建独立卡片，其交易会归入账单对应的主卡，同时保留原始交易卡尾作为历史证据。只有多个卡尾或普通合并账单、但没有明确主副卡信息的模板继续沿用原有套卡逻辑，不会据此推断业务关系。

本版本为已有安装提供一次历史账单更新入口。系统会根据实际存在的受影响银行合并询问，用户确认后重新核对数据库已经记录的历史账单邮件；新安装不会显示该提示。更新过程保留用户完善的卡号、别名、加密信息和手动年费日，并支持邮件缺失、解析失败、邮箱连接失败和容器重启后的安全恢复。

## 详细变更

### 1. 建立主卡、副卡和附属卡关系

- 卡片新增只读的业务身份、归属主卡和业务组成员信息，业务主卡由明确账单决定，用户不能手动更换。
- 主卡固定作为整组封面，展开卡组时主卡排在最前；副卡和附属卡只在组内详情中显示。
- 主卡统一承接账单、未取得账单、还款状态和提醒；副卡与附属卡不再单独生成上述内容。
- 副卡继承主卡持卡人；附属卡使用自己的持卡人。两者均可独立维护别名、卡片信息和年费日。
- 主卡冻结、注销或删除时同步整组；副卡和附属卡仍可单独冻结、注销或删除。
- 既有“设为主卡”继续只用于普通同周期套卡的列表封面，不参与明确业务关系，也不会改变银行确定的业务主卡。

### 2. 支持首批明确关系模板

- 工商银行：账单承接卡识别为主卡，实体关联卡识别为副卡，手机信用卡交易归入主卡且不创建卡片档案。
- 平安银行：识别账单中的主卡与附属卡区块，并按产品和明确账单证据建立归属。
- 广发银行：识别主卡以及账单明确标注的附属卡。
- 解析器注册信息新增“能够提供明确业务关系”的能力标记，后续新增模板可复用同一套入库与升级机制。
- 普通多卡尾和合并账单继续保持原有行为，系统不会只凭同封邮件或相同账期推断主副卡关系。

### 3. 增加历史账单更新流程

- 旧版本首次升级时，系统只在数据库中存在受影响模板的历史账单后生成一次合并提示，银行名称按实际数据展示。
- 用户可以立即更新、暂不更新、查看进度或重试失败任务；界面只展示更新原因和结果，不暴露邮件读取等后台细节。
- 系统处理数据库已经记录的全部相关历史账单，不限制账期，也不会扫描未知营销邮件。
- 单封邮件成功读取并解析后才更新对应数据；邮箱中已经删除的邮件会被忽略并保留现有账单，解析或连接失败会保留旧数据并允许重试。
- 任务进度持久化保存，容器重启后可以继续；更新不会重置邮箱游标、标记邮件已读或保存邮件正文。
- 孤立卡片只有在历史证据完整、由邮件自动创建、已经没有有效关联且不含用户数据时才允许清理。

### 4. 更新卡片与账单界面

- 卡面左上角使用斜向袖标显示“主卡”“副卡”或“附属卡”，并调整标题间距，避免遮挡设置入口和银行名称。
- 明确业务组的列表只显示主卡和卡片数量；组内副卡、附属卡不重复显示主卡的出账日、还款日和本期应还。
- 子卡编辑界面明确展示卡片身份与归属主卡，只开放允许单独维护的信息。
- 账单记录保持整组一条账单、一个还款入口；交易明细仍按实际消费卡片展示卡尾。
- 修正邮箱绑定页面 SSL 选项在桌面布局中的对齐。

### 5. 扩展接口、迁移与测试

- 卡片接口新增业务角色、归属主卡、业务组成员和账单设置可编辑状态，这些关系字段均为只读。
- 新增历史更新任务的查询、确认、跳过、进度和重试接口。
- 数据库新增卡片业务关系、手机卡别名、交易原始卡尾以及持久化升级任务结构。
- 增加解析、合账、卡片接口、状态级联、删除级联、账单去重、提醒去重、历史更新和前端交互测试。
- 邮件解析依赖升级到 `mailparser 3.9.17`，同步采用已经修复递归对象合并风险的 `deepmerge-ts 8.0.2`。

## 升级说明

- 从 `v0.2.3` 升级时，保留原有 `.env`、`ENCRYPTION_KEY`、数据库和 Docker 数据卷，仅将 `APP_VERSION` 改为 `0.3.0` 后重新拉取并启动容器。
- 内置 MySQL：执行 `docker compose pull`，然后执行 `docker compose up -d`。
- 外置 MySQL：执行 `docker compose -f docker-compose.external.yml pull`，然后执行 `docker compose -f docker-compose.external.yml up -d`。
- 容器启动时会自动执行本版本的 Prisma 数据库迁移；升级前建议备份数据库，但不要清理账单、卡片或邮箱同步记录。
- 已有工商银行、平安银行或广发银行历史账单的系统可能显示“更新历史账单”。用户确认后，系统会重新核对实际存在的相关历史账单；用户也可以暂不更新并继续使用现有数据。
- 历史更新需要原邮箱账户仍可连接。已经从邮箱删除的邮件不会导致任务失败，系统会保留对应的现有账单数据。
- 升级过程中不得更换 `ENCRYPTION_KEY`；否则已经保存的完整卡号、有效期和 CVV 将无法解密。

## 已知限制

- 主卡、副卡和附属卡关系只在银行账单明确提供证据时建立；首批支持工商银行、平安银行和广发银行的现役模板。
- 只有多个卡尾或普通合并账单的模板不会自动推断业务关系，仍按同账期套卡展示。
- 历史账单更新只能重新核对数据库已经记录的账单邮件；邮箱中已删除的邮件会保留原数据，但无法补充新的关系证据。
- 银行调整邮件格式后可能需要新增版本化解析器；解析失败不会覆盖已有账单。
- 服务端 `npm audit` 仍报告 1 项中危和 4 项高危上游传递依赖告警：Prisma 命令行工具仍依赖 `deepmerge-ts 7.x`，Prisma 的 MariaDB 适配器仍固定使用 `mariadb 3.4.5`。当前兼容版本没有完整修复，强制自动修复会降级 Prisma 主版本，因此本版本没有采用破坏性降级。外置数据库应部署在可信私有网络中，并继续跟进 Prisma 上游更新。
- 浦发银行邮件不包含可直接解析的交易明细，跳转页需要短信验证，因此只能获取账单摘要。
- 未出账单日度明细目前仅支持招商银行“每日信用管家”，并且只同步本账期数据。
- 纯 HTTP 访问不提供传输加密；建议通过 HTTPS 反向代理使用。
